# Pi 4B capacity probe — 2026-09-30

## Scope / reproducibility

Cortex-A72, max 1.8GHz, 4 cores; Linux aarch64; Clang 19.1.7; caller CPU3, consumer CPU2, no exclusive CPU isolation. `-std=c++14 -O3 -DNDEBUG -fno-exceptions -fno-rtti -DFLUX_FOUNDRY_NO_EXCEPTION_STRICT=1 -pthread -march=native -Wall -Wextra -Werror`. Environment, original git revision and source SHA-256 are in `pi4b-20260930-env.txt`; executor sizes are in `pi4b-20260930.log`.

```bash
CXX=clang++ EXTRA_CXXFLAGS='-march=native -Wall -Wextra -Werror' \
  bash bench/queue_capacity/run.sh --samples 32768 --repeats 3 \
  --producer-cpu 3 --consumer-cpu 2 > /tmp/capacity.csv
python3 bench/queue_capacity/summarize.py /tmp/capacity.csv
```

Matrix: 4 capacities × 3 lanes × 5 profiles × 3 repetitions = **180 cases / 5,898,240 events**. Each event performs 128 identical unsigned dependency-chain work iterations and one executor dispatch. This is an instrumented synthetic task, not a real strategy or NIC-to-order benchmark. All finite scheduled events completed; no dropped or omitted scheduled arrivals. Every case validates exactly-once successful completion, checksum and timestamp order. Detailed per-run rows: `pi4b-20260930.csv`; medians and ranges: `pi4b-20260930-summary.md`.

Release correctness smoke and UBSan each passed 60 cases × 1024 events. During development, UBSan found over-aligned executor allocation via plain C++14 `new` in the harness; corrected to the existing ff aligned allocator before these published results. ASan **did not run**: its runtime failed at startup reserving its address space (`sanitizer_allocator_primary64.h:133`). No production executor semantics changed. No TSan run, no full existing repository suite rerun (only standalone benchmark/docs added), no multi-producer or sustained soak test.

## Findings

### 1. Low offered load: capacity does not determine baseline latency

At 100k events/s, median-of-run fast E2E p99 is 2.81–2.84us across all capacities; raw is 2.45–2.50us, normal 3.70–3.98us. These numbers include work and instrumentation. Some individual fast runs reached p99 31–35us despite low outstanding counts: ordinary shared-host tail variation is present and a three-run median must not hide it.

At 500k/s fast sustains the offered rate, with E2E p50 about 1.76us. Its per-run p99 varies from 4.18us to 122.21us. **All fast steady500k runs have peak outstanding <=122**, below even capacity 256. Therefore the apparent nicer p99 at capacity 16384 is not evidence that increasing capacity fixed queue-full pressure in this profile; capacity order and shared-host disturbances remain confounders.

### 2. A finite consumer pause: larger capacity buffers it without eliminating waiting

Fast, 500k arrivals/s, one 5ms consumer sleep (medians of three runs):

| Capacity | Planned-arrival E2E p99 | Submit lag p99 | Peak outstanding |
|---:|---:|---:|---:|
| 256 | 4.848ms | 4.333ms | 258 |
| 1024 | 4.852ms | 2.801ms | 1026 |
| 4096 | 4.882ms | 0.161us | 2537 |
| 16384 | 4.891ms | 0.141us | 2546 |

500k/s × 5ms is approximately 2500 planned arrivals, consistent with the observed outstanding work. Capacity 4096 can absorb this particular pause without significant producer lag; 16384 offers little extra benefit here. The E2E tail still includes the consumer's pause. Capacity 256 appears to have only 351us actual-submission p99, versus 4.848ms planned-arrival p99: measuring after backpressure would hide most of the actual wait upstream.

This is not a general rule that 4096 is optimal: required burst budget depends on real arrival rate, service rate, pause duration and event size.

### 3. Sustained overload: capacity relocates the backlog, it does not create service capacity

Fast at 2M planned events/s: observed finite-run completed rate is 0.714–0.775M/s; E2E p99 is 25.67–29.27ms for the different capacities. Increasing 256→16384 reduces submit-lag p99 26.74→9.09ms, but actual-submission p99 increases 0.373→16.65ms. Much of the backlog moved from upstream into the executor. No capacity keeps up with the offered rate in this workload.

Normal is near/above its sustainable rate already at 500k/s in this probe: completed rates 0.465–0.496M/s, median-of-run E2E p99 1.01–5.41ms. At 2M/s, completed rates 0.398–0.527M/s and E2E p99 45.41–65.56ms. Larger capacity does not consistently improve throughput and sometimes worsens it. Cache footprint, allocation/ownership lifetime and contention are plausible profiling leads, **not established causes**.

### 4. Burst batching: a large buffer is not automatically a latency win

8192-event bursts every 20ms: fast E2E p99 stays around 10.71–11.15ms across capacities. Bigger queues reduce submit lag, but processing the burst still costs time. Normal p99 increases from 15.82ms (256) to about 18.82–19.41ms (large capacities) in these runs. These are finite-run rates, not infinite-stream throughput estimates: the final burst finishes before the next nominal period.

## Practical starting point

For **this** 500k/s + 5ms-pause budget, 4096 is a reasonable starting capacity for the fast lane. Keep synchronous hot work on its owner, and use explicit admission/backpressure policies rather than treating queue growth as a cure for overload. Executor object sizes: 256=32,960 bytes; 1024=131,264; 4096=524,480; 16384=2,097,344. These exclude queued flow allocations and sample storage.

Next meaningful tests: realistic strategy work, multi-producer fan-in, longer fixed-arrival runs with randomized capacity ordering, and profiling the normal path. None of these results establishes hard real-time or production trading suitability.
